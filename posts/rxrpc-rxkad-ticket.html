When decryption fails but parsing continues: an rxkad ticket bug

First posted 2026-04-08 · merged into mainline 2026-04-08 · rxrpc, rxkad, crypto API

RxRPC is the kernel's RPC transport, best known as the protocol underneath AFS. Its rxkad security class authenticates peers by exchanging encrypted tickets. This post is about a missing return-value check in the ticket decryption path — a one-line-class bug with a long pedigree.

The bug

When a RESPONSE packet arrives, rxkad_decrypt_ticket() decrypts the embedded ticket and then parses the result as plaintext: extracting addresses, lifetimes, key material, and so on. The decryption call looked like this:

skcipher_request_set_crypt(req, sg, sg, ticket_len, iv.x);
crypto_skcipher_decrypt(req);
skcipher_request_free(req);

p = ticket;
end = p + ticket_len;
/* parse away... */

The return value of crypto_skcipher_decrypt() was simply discarded. But decryption can fail — most obviously when the ticket length is not a multiple of the cipher block size. A malformed RESPONSE can pick exactly such a length, make the decrypt operation fail, and the code then cheerfully drives the ticket parser over whatever bytes are in the buffer: attacker-controlled ciphertext, never touched by the cipher at all.

The fix

Check the result, and treat a failed decrypt like any other bad ticket — abort the connection with RXKADBADTICKET:

ret = crypto_skcipher_decrypt(req);
skcipher_request_free(req);
if (ret < 0)
	return rxrpc_abort_conn(conn, skb, RXKADBADTICKET, -EPROTO,
				rxkad_abort_resp_tkt_short);

After the fix, a ticket that cannot be decrypted never reaches the parser. The abort also carries a distinct tracepoint tag (rxkad_abort_resp_tkt_short), so the failure is observable when debugging.

How old was it?

The Fixes: tag points to 17926a79320a ("[AF_RXRPC]: Provide secure RxRPC sockets…") — the original rxkad implementation. The unchecked call had been sitting there essentially since the code existed, surviving every refactor of the crypto API around it. A nice reminder that "the code is old" is not evidence that it is correct; it's often the opposite.

Upstream

David Howells picked the fix up into his rxrpc series, and it landed in mainline as fe4447cd9562 ("rxrpc: reject undecryptable rxkad response tickets"), with a stable backport.

Takeaway: in security-critical paths, an unchecked crypto_* return value is never a style issue. Assume every cryptographic operation can fail, and decide explicitly what the failure means before the data moves on.
