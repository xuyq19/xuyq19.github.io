Yocto 构建踩坑记录

2025.05 · 徐宇奇 · 阅读约 12 分钟

OpenBMC 基于 Yocto 构建系统，开发过程中几乎每天都在和 bitbake 打交道。本文记录我在实际项目中遇到的各种坑和解决方法，希望能帮后来者少踩一些雷。

一、Recipe 编写常见错误

1.1 SRC_URI 的 git 协议问题

很多 Yocto 教程里用 git:// 协议，但企业环境通常有代理限制，GitHub 也逐步弃用 git 协议。建议统一使用 https://：

SRC_URI = "git://github.com/openbmc/phosphor-networkd;branch=master;protocol=https"
# 上面的写法在某些网络环境下会失败，改为：
SRC_URI = "git://github.com/openbmc/phosphor-networkd;branch=master;protocol=https"

1.2 依赖声明不全

OpenBMC 的 D-Bus 服务依赖经常遗漏。如果你写了一个新服务，但运行时 dbus 报错 No such interface，通常是 DEPENDS 或 RDEPENDS 没写完整：

DEPENDS += " \
    phosphor-dbus-interfaces \
    sdbusplus \
    systemd \
"
RDEPENDS:${PN} += " \
    phosphor-dbus-interfaces \
    systemd \
"

二、Bitbake 构建问题

2.1 并行构建失败

默认 bitbake 会用多线程并行编译，但 OpenBMC 某些 recipe 有隐式依赖关系，并行会导致 race condition：

# 在 local.conf 中限制并行度
BB_NUMBER_THREADS = "4"
PARALLEL_MAKE = "-j 4"

# 或者针对特定 recipe 禁用并行
do_compile[no_parallel] = "1"

2.2 缓存失效问题

修改了代码但 bitbake 没有重新编译，这是因为 sstate 缓存认为没有变化。强制重建：

bitbake -c cleansstate 
bitbake 

# 或者全局清理（慎用）
rm -rf tmp/

三、SDK 与交叉编译

OpenBMC 的目标平台通常是 ARM（ASPEED）或 x86，需要在宿主机上生成 SDK 来交叉编译：

# 生成 SDK
bitbake obmc-phosphor-image -c populate_sdk

# 安装 SDK 后 source 环境
source /path/to/sdk/environment-setup-armv7ahf-vfpv4d16-openbmc-linux-gnueabi

# 验证交叉编译器
$CC --version

四、OpenBMC 特有陷阱

4.1 D-Bus 接口变更未同步

如果你修改了 phosphor-dbus-interfaces 的 YAML 接口定义，但其他服务没有重新编译，会出现 D-Bus 方法调用失败。需要在 layer 依赖中正确声明：

LAYERSERIES_COMPAT_your-layer = "nanbield"

4.2 镜像大小超出 Flash 限制

OpenBMC 的 Flash 通常只有 64MB 或 128MB，如果镜像太大：

  • 使用 IMAGE_FEATURES += "read-only-rootfs" 减少可写层
  • 精简不必要的 systemd 服务和软件包
  • 将 /var 挂载到 tmpfs，避免写入 flash

五、总结

Yocto 的学习曲线陡峭，但一旦掌握规律，构建问题大多可以归类为：依赖声明、缓存管理、并行控制和交叉编译环境。建议遇到问题时先看 bitbake -e 的输出，确认环境变量和路径是否正确。
