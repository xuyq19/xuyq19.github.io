An off-by-a-message offset in bpf_msg_push_data()

First posted 2026-05-24 · merged into mainline 2026-05-29 · bpf, sockmap, scatterlist

Some of the most satisfying kernel fixes are one-liners. This is the story of one in the sockmap BPF helper bpf_msg_push_data(), where a single wrong operand corrupted the scatterlist layout of a socket message.

What the helper does

bpf_msg_push_data() lets a sk_msg BPF program insert bytes into the middle of a message. Messages are stored as a scatterlist of page fragments. When the insertion point falls inside an existing SG entry, the helper splits that entry in two: a left fragment covering everything before the insertion point, and a right fragment covering everything after it.

The bug

The split code adjusts the right fragment like this:

psge->length = start - offset;
rsge.length -= psge->length;
rsge.offset += start;

The problem is the last line. rsge.offset is page-local — an offset inside the page backing that SG entry. But start is message-global — the insertion point counted from the beginning of the whole message, spanning however many SG entries came before.

For an insertion into the very first SG entry the two happen to coincide (offset == 0), so the bug hides. For any later entry, the offset is advanced by far too much, and the split layout becomes inconsistent: the right fragment points somewhere past where it should, and the bytes don't add up.

The fix

Advance the offset by the fragment-local delta instead — exactly the number of bytes the left fragment absorbed from the front of the original entry:

-rsge.offset += start;
+rsge.offset += start - offset;

Since psge->length = start - offset was computed on the line above, the invariant is easy to verify: left length + right length = original length, and right offset = original offset + left length.

Upstream

Merged as f72eed9b84fb ("bpf: sockmap: fix tail fragment offset in bpf_msg_push_data"), with a Fixes: tag to 6fff607e2f14, the commit that introduced the helper, and a stable backport.

Takeaway: whenever two coordinate systems meet — message-global versus page-local here — write down which variable lives in which. The bug was one missing subtraction; the audit to find it was the real work.
